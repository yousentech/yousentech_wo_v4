# خارطة طريق نظام العناية بالسيارات — Odoo 17

## مبادئ ثابتة

- Odoo هو مصدر الحقيقة لقواعد الأعمال والصلاحيات والشركات.
- واجهة Odoo وتطبيق Flutter يستدعيان العمليات النموذجية نفسها؛ لا يتكرر المنطق.
- العقود الخارجية تستخدم `public_uuid` والأكواد التقنية، لا أسماء العرض أو IDs الداخلية.
- كل مرحلة تتضمن تصميم الشاشة، قواعد الأعمال، الصلاحيات، التوثيق، وعقد API واختباراته.

## المرحلة 0 — تثبيت الأساس

الحالة: اجتازت مراجعة الاعتماد الساكنة؛ اختبار Odoo الفعلي شرط قبل الإنتاج.

- إصلاح النماذج الناقصة والاعتماديات.
- فصل صلاحيات الاستقبال والفني والمشرف والمحاسب والمدير ومسؤول التهيئة.
- منع منح `base.group_system` لمدير المركز.
- إضافة UUID عام ومصدر العملية وسجل التدقيق.
- ترحيل تمهيدي للأكواد وUUID عند الترقية من النسخة السابقة.
- تأسيس استجابة API موحدة وعقد أخطاء وتعدد شركات في التوثيق.
- اختبارات: Python، XML، external IDs، المراجع، الصلاحيات، وعقد OpenAPI.

## المرحلة 1 — محرك التهيئة الذاتية

الحالة: MVP اجتاز مراجعة الاعتماد الساكنة؛ اختبار Odoo الفعلي شرط قبل الإنتاج.

- تهيئة أولى من خمس خطوات قابلة للحفظ والاستكمال.
- ملف دائم واحد لكل شركة.
- قوالب idempotent للخدمات والأفلام والأجزاء.
- سعر أساسي افتراضي، والتسعير حسب الحجم والعمولات خيارات متقدمة.
- مركز إعدادات ولوحة جاهزية منفصلان عن الويزارد.
- API: ملف الشركة، قراءة الجاهزية، حفظ خطوة، تطبيق قالب وتفعيل — مخطط، غير منشور بعد.

## المرحلة 2 — أمر التركيب الأساسي

الحالة: Installation Order MVP منفذ واجتاز الفحص الساكن؛ اختبار Odoo الفعلي
شرط قبل الإنتاج.

- لوحة كانبان وقائمة وبحث، ونموذج عربي RTL متجاوب.
- استقبال العميل والسيارة والموعد وتوزيع المستشار والمشرف والفنيين.
- محرر مباشر للخدمة والفيلم والدرجة والجزء دون نوافذ متداخلة.
- تطبيق سعر حجم السيارة أو السعر الأساسي، وتفسير المصدر، وتجاوز يدوي محمي
  بصلاحية وسبب وسجل تدقيق.
- انتقالات خادمية: مسودة ← موعد/وصول ← استلام وفحص ← تنفيذ ← جودة ← جاهز
  ← تم التسليم، مع إلغاء بسبب إلزامي وإعادة من الجودة إلى التنفيذ.
- توثيق صور قبل/بعد، حالة الاستلام، تقدم الخدمات، المواد التشغيلية، موافقة
  العميل، وروابط أمر البيع والفاتورة والضمان دون إنشاء بيانات محاسبية مكررة.
- سجل زمني append-only وUUID عام ومصدر عملية ومفتاح idempotency لإنشاء الأمر.
- تطبيق العمليات أصبح ظاهرًا لكل أدوار نظام العناية، بينما تبقى التهيئة
  المتقدمة محجوبة حسب الدور.
- API: عقد `/api/v1/installation-orders` وعمليات المراحل مخطط في OpenAPI؛
  لا توجد REST controllers منشورة.

## المرحلة 3 — التنفيذ الفني والفحص

الحالة: مخطط.

- تطوير ما بعد MVP: مؤقتات متعددة/إيقاف واستئناف، المقاسات التفصيلية، رقم
  الرولة، قوائم فحص قابلة للتهيئة، واعتمادات صور أكثر تفصيلًا.
- تحويل المواد المسجلة في أمر التركيب إلى صرف مخزني فعلي مضبوط.
- شاشات mobile-first للفني.
- API: مزامنة محدودة باستخدام `write_date` وcursor، وIdempotency-Key لنتيجة التنفيذ.

## المرحلة 4 — الدفعات والفوترة والمخزون

الحالة: مخطط.

- الدفعات الجزئية، أمر البيع، الفاتورة، الضريبة والصرف المخزني.
- المبالغ في API مع `amount`, `currency`, `precision`.
- تسجيل الدفعة idempotent ومنع التكرار عند ضعف الشبكة.

## المرحلة 5 — الضمان والعمولات

الحالة: مخطط.

- إصدار الضمان، المطالبات، تغيير الأجزاء واحتساب العمولات واعتمادها.
- فصل بيانات العميل Portal عن API الموظفين.
- أحداث تدقيق لكل إصدار أو تغيير أو اعتماد.

## المرحلة 6 — الترحيل والجودة والإطلاق

الحالة: مخطط.

- ترحيل بيانات Odoo 13 بأكواد مرجعية ومطابقة موثقة.
- اختبارات contract وintegration وsecurity للـAPI.
- تجربة فرع واحد، ثم إطلاق تدريجي.
- تطبيق Flutter يبدأ بعد اعتماد العقود والأمان والشاشات التشغيلية.

## بوابة الانتقال للمرحلة 3

- تثبيت/ترقية الموديول بنجاح على Odoo 17 فعلي.
- اختبار التهيئة وأوامر التركيب لشركتين على الأقل، بما فيها منع الوصول المتبادل.
- اختبار كل انتقال، وفشل الجودة، والإلغاء، والتسعير حسب الحجم وتجاوز السعر.
- اختبار النموذج والكانبان على سطح المكتب والتابلت والجوال داخل Odoo.
- مراجعة أمن المصادقة قبل نشر `/api/v1`.
- اعتماد UX لأمر التركيب والتوثيق وعقد الأخطاء من مالك المنتج.
