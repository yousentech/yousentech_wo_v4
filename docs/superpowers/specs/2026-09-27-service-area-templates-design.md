# تصميم نماذج مناطق الخدمة

## الهدف
إضافة طبقة «النموذج» بين منطقة الخدمة والمكونات بحيث يمكن لمنطقة خدمة واحدة مثل «كامل السيارة» امتلاك أكثر من تركيبة مكونات، مع نموذج افتراضي واضح يمكن الاعتماد عليه لاحقًا في أمر التركيب.

## النطاق الحالي
هذا الإصدار يبني أساس الإعداد والبيانات والواجهة فقط. لا يغيّر منطق أمر التركيب الحالي ولا التسعير الحالي إلا بالقدر اللازم لربط المكونات بالنموذج دون فقد البيانات القديمة.

## الهيكل المعتمد
الهيكل يصبح:

`منطقة الخدمة -> النموذج -> المكونات`

- منطقة الخدمة تبقى الكيان الرئيسي الحالي ولا تُستبدل.
- يضاف كيان دائم جديد للنموذج مرتبط بمنطقة خدمة واحدة.
- كل نموذج يحتوي مجموعة المكونات التابعة له.
- كل منطقة خدمة يمكن أن تحتوي نموذجًا واحدًا أو أكثر.
- يوجد نموذج افتراضي واحد فقط لكل منطقة خدمة.
- إذا كانت منطقة الخدمة تحتوي نموذجًا واحدًا فقط فهو الافتراضي تلقائيًا.
- عند جعل نموذج جديد افتراضيًا، تزال صفة الافتراضي من بقية نماذج المنطقة نفسها تلقائيًا.
- لا يسمح بحالة فيها أكثر من نموذج افتراضي للمنطقة الواحدة.

## التوافق مع البيانات الحالية
يجب الحفاظ على بيانات العملاء الحالية. عند الترقية، كل منطقة خدمة حالية لديها مكونات تُنشأ لها تلقائيًا نسخة نموذج افتراضي باسم مناسب مثل «النموذج الأساسي»، ثم تُربط مكوناتها الحالية به. لا تُحذف المكونات ولا تتغير أسعارها أو عمولاتها أو علاقاتها الحالية نتيجة الترحيل.

يجب أن يبقى الوصول الحالي إلى المكونات صالحًا أثناء الانتقال حتى لا تنكسر الشاشات أو منطق التسعير القائم. أي حقل ربط جديد يبدأ بطريقة متوافقة مع السجلات القديمة ثم يملأه migration بصورة حتمية.

## نموذج البيانات
يضاف model جديد مخصص للنماذج، باسم تقني يتبع naming الحالي للموديول، ويحتوي على الأقل:

- `name`: اسم النموذج، مطلوب.
- `service_area_id`: منطقة الخدمة، مطلوب، مع حذف cascade أو سياسة متوافقة مع علاقة المنطقة الحالية بالمكونات.
- `is_default`: هل هو النموذج الافتراضي.
- `sequence`: ترتيب العرض.
- `active`: للأرشفة بدل الحذف عند الحاجة.
- علاقة بالمكونات الموجودة حاليًا دون إنشاء نسخة مكررة من مفهوم المكوّن.

المكوّن الحالي يحصل على مرجع للنموذج الذي ينتمي إليه. لا ننشئ نظام مكونات موازيًا.

## قواعد النزاهة
- لا يوجد نموذج بلا منطقة خدمة.
- المكوّن المرتبط بنموذج يجب أن تكون منطقة خدمته متوافقة مع منطقة خدمة النموذج.
- لا يوجد أكثر من default واحد داخل منطقة خدمة.
- إذا بقي نموذج واحد فقط بعد إنشاء/حذف/أرشفة النماذج، يصبح هو الافتراضي.
- لا يجوز حذف/أرشفة النموذج الافتراضي إذا كان ذلك سيترك منطقة الخدمة التي لديها نماذج أخرى بلا default؛ يجب تعيين بديل بصورة آمنة أو منع العملية برسالة واضحة.

## واجهة الإعداد
في شاشة/معالج إعداد الفيلم الحالية، عرض المكونات يتغير من مستويين إلى ثلاثة مستويات:

1. منطقة الخدمة.
2. النموذج داخل المنطقة.
3. المكونات داخل النموذج.

من بطاقة منطقة الخدمة يستطيع المستخدم رؤية النماذج وإضافة نموذج وتعديل اسمه وتحديد الافتراضي. النموذج الافتراضي يظهر بتمييز بسيط وواضح دون تكبير الكروت أو تغيير المقاس المرجعي للـ popup. فتح/طي النموذج يعرض مكوناته، وتبقى إجراءات إضافة/تعديل المكونات الحالية تعمل في سياق النموذج المختار.

يجب الحفاظ على RTL/LTR الحالي، الخطوط الحالية، الهيدر والفوتر الثابتين، ومقاس نافذة «مركز تهيئة النظام» المعتمد. لا يعاد تصميم بقية مراحل الـ wizard ضمن هذا التغيير.

## التسعير والعمولات
لا ننقل سعر منطقة الخدمة أو العمولة إلى النموذج في هذه المرحلة. النموذج يحدد «تركيبة المكونات» فقط. منطق السعر والعمولة الحالي يبقى كما هو لتجنب خلط تغيير هيكلي بتغيير تجاري مستقل.

## أمر التركيب
لا يتم تعديل اختيار الخدمات أو إنشاء سطور أمر التركيب في هذه المرحلة. الهدف هو توفير `default template` موثوق يمكن ربط أمر التركيب به في مرحلة لاحقة. يجب ألا يتغير السلوك الحالي لأوامر التركيب بعد تثبيت هذا الإصدار.

## الترحيل
ترفع نسخة الموديول من الإصدار الحالي `17.0.4.0.91` إلى إصدار تالٍ مناسب. يضاف migration يقوم بصورة idempotent بـ:

1. اكتشاف مناطق الخدمة الحالية.
2. إنشاء نموذج أساسي افتراضي فقط عندما لا يوجد نموذج مناسب مسبقًا.
3. ربط المكونات الحالية بالنموذج الأساسي دون تكرار سجلات.
4. إصلاح أي حالة default غير مكتملة بصورة حتمية.
5. عدم تعديل الأسعار والعمولات والمنتجات والبيانات التشغيلية الأخرى.

## الأمان والصلاحيات
صلاحيات النموذج الجديد تتبع صلاحيات إعداد مناطق الخدمة/المكونات الحالية. لا يفتح model الإعداد لمستخدمين لا يملكون أصلًا صلاحية إدارة التهيئة.

## الاختبارات المطلوبة
- إنشاء أول نموذج يجعله default تلقائيًا.
- إنشاء نموذج ثانٍ لا ينتج default مزدوجًا.
- تبديل default يلغي السابق.
- نقل/إنشاء مكوّن داخل نموذج يحافظ على تطابق منطقة الخدمة.
- migration لبيانات قديمة ينشئ نموذجًا واحدًا ويربط كل المكونات بلا فقد أو تكرار.
- إعادة تشغيل migration لا تنشئ نسخًا إضافية.
- الواجهة تعرض التسلسل منطقة -> نموذج -> مكونات وتبقي إجراءات المكونات الحالية عاملة.
- static validation للموديول ينجح.
- smoke test لترقية الموديول على قاعدة اختبار ينجح دون registry/XML errors.
- regression: منطق التسعير وأمر التركيب الحالي لا يتغير.

## خارج النطاق
- اختيار نموذج يدوي داخل أمر التركيب.
- تغيير السعر أو العمولة حسب النموذج.
- نماذج حسب نوع السيارة أو المقاس أو الوكالة.
- نسخ نموذج من منطقة خدمة إلى أخرى.
- إعادة تصميم شاملة للـ wizard.

هذه البنود يمكن إضافتها لاحقًا بعد تثبيت طبقة النماذج الأساسية.
