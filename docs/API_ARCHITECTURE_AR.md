# معمارية التكامل مع Flutter وواجهة API

## حالة التنفيذ

المرحلة الحالية API-ready على مستوى نموذج البيانات وعمليات الأعمال والتوثيق.
لا توجد REST controllers منشورة. نشر `/api/v1` ينتظر مراجعة الأمان واختيار موفر
المصادقة.

## الحدود

- Odoo يملك البيانات وقواعد التسعير والتحقق والصلاحيات.
- Flutter واجهة عميل ولا يعيد تنفيذ قواعد الأعمال محليًا.
- العمليات الأساسية تكون model/service methods؛ أزرار Odoo وAPI أغلفة رقيقة لها.
- لا تستخدم `onchange` كضمان لصحة البيانات؛ القيود والتحقق تعمل على النموذج.
- حقول دورة حياة التهيئة محمية من `write` العام، والانتقال يتم فقط عبر عمليات
  البدء والحفظ والتقدم والتراجع والتفعيل وإعادة الفتح.
- دورة أمر التركيب محمية بالطريقة نفسها. أزرار Odoo تستدعي عمليات النموذج:
  `action_confirm_arrival`, `action_complete_intake`, `action_start_execution`,
  `action_submit_quality`, `action_return_to_execution`, `action_pass_quality`,
  `action_deliver`, `action_cancel`. controller المستقبلي يستدعي العمليات
  نفسها ولا يكتب `state` أو توقيتات التدقيق مباشرة.

## التعريفات العامة

- كل كيان يظهر خارجيًا يحمل `public_uuid` غير قابل للتخمين وفريدًا.
- الشركة والمستخدم والعميل والمنتج الأساسي تحمل الحقل الداخلي
  `wof_public_uuid` ويعرضه serializer مستقبلًا باسم `public_uuid`.
- العقود تستخدم أكواد تقنية مثل `tint`, `ready`, `SMALL`، ولا تعتمد على الاسم
  العربي أو ID داخلي.
- أسماء العرض مترجمة ويمكن تغييرها دون كسر التطبيق.

## Versioning والاستجابات

المسار الأساسي المخطط `/api/v1`.

نجاح:

```json
{"success": true, "data": {}, "meta": {"request_id": "uuid"}}
```

خطأ:

```json
{
  "success": false,
  "error": {
    "code": "SETUP_NOT_READY",
    "message": "أكمل البيانات المطلوبة قبل تفعيل النظام.",
    "validation": [{"field": "service_line_ids", "code": "required"}]
  },
  "meta": {"request_id": "uuid"}
}
```

القوائم تضيف `page`, `page_size`, `next_cursor`, `total` عند ملاءمة حساب الإجمالي.
لا تظهر stack traces أو أسماء جداول أو استعلامات.

## المصادقة

- موظفو المركز: OAuth2/OIDC إذا توفر موفر موثوق، أو token sessions آمنة تنشأ
  خادميًا بعد مراجعة الأمان.
- لا تُخزن كلمة مرور Odoo في Flutter ولا مفاتيح ثابتة داخل التطبيق.
- لا يُنشأ JWT مخصص داخل الموديول.
- Portal العميل سيكون نطاقًا منفصلًا عن API الموظفين وصلاحياته أقل.

## الصلاحيات والشركات

- كل طلب ينفذ بهوية مستخدم Odoo فعلية.
- تطبق ACL وrecord rules و`allowed_company_ids`.
- `company_uuid` في الطلب يجب أن يكون ضمن الشركات المسموحة.
- لا يستخدم `sudo` لتنفيذ عمليات الموظفين أو قراءة بياناتهم.
- الاستثناءان الحاليان هما إدراج صف سجل التدقيق وإدراج حدث السجل الزمني
  لأمر التركيب. كلاهما append-only ويبنيه الخادم بعد نجاح ACL والشركة والدور
  والحالة؛ لا يملك المستخدمون صلاحية إنشائهما أو تعديلهما.
- الخدمات والأفلام والأجزاء والأسعار والتهيئة بيانات معزولة حسب الشركة.
  الشركات المصنعة والطرازات والسنوات والوكالات قوائم مرجعية مشتركة بلا بيانات عميل.

## Idempotency

إنشاء أمر التركيب أصبح idempotency-ready على مستوى النموذج عبر
`create_idempotent(values, key)`: يخزن المفتاح وبصمة الطلب ضمن الشركة، ويعيد
السجل نفسه عند تكرار الطلب المطابق، ويرفض اختلاف المحتوى بالكود
`IDEMPOTENCY_CONFLICT`. لا يصبح هذا عقدًا شبكيًا حتى تنفيذ controller الآمن.

العمليات الحساسة المخططة تقبل `Idempotency-Key`:

- إنشاء أمر تركيب.
- تسجيل دفعة.
- رفع نتيجة تنفيذ أو تسليم.

في الدفعات والنتائج المستقبلية سيخزن المفتاح مع المستخدم والشركة ونوع العملية
وبصمة الطلب والنتيجة. إعادة نفس الطلب تعيد النتيجة، وتغيير المحتوى مع نفس
المفتاح يعطي `IDEMPOTENCY_CONFLICT`.

## عقد أمر التركيب المخطط

المورد الأساسي `/api/v1/installation-orders` ويستخدم `orderUuid`. حالات دورة
الحياة أكواد ثابتة:

`draft` → `scheduled` → `intake` → `in_progress` → `quality` → `ready`
→ `delivered`.

`cancelled` نهاية بديلة، و`quality` يمكن أن تعود إلى `in_progress` مع ملاحظة.
لا يقبل body حالة أو مستخدمًا أو توقيتًا. العمليات موثقة كمسارات action مستقلة
في OpenAPI لتكون الصلاحية والخطأ وidempotency واضحة.

خط الخدمة يستخدم UUID وأكواد الخدمة والفيلم والجزء. Odoo يحسب سعر الحجم أو
السعر الأساسي والضريبة والخصم والإجمالي. Flutter لا يعيد حسابها ولا يعتمد على
الاسم العربي أو `id`.

أكواد أخطاء المجال المخططة تشمل:

- `ORDER_NOT_FOUND`
- `ORDER_DATA_INCOMPLETE`
- `INVALID_STATE_TRANSITION`
- `PRICE_NOT_CONFIGURED`
- `PRICE_OVERRIDE_FORBIDDEN`
- `DISCOUNT_LIMIT_EXCEEDED`
- `TECHNICIAN_REQUIRED`
- `TECHNICIAN_NOT_ASSIGNED`
- `EXECUTION_INCOMPLETE`
- `QUALITY_NOT_PASSED`
- `CUSTOMER_APPROVAL_REQUIRED`
- `IDEMPOTENCY_CONFLICT`

## التواريخ والمبالغ

- التواريخ UTC بصيغة ISO-8601، مثال `2026-07-30T12:00:00Z`.
- واجهة المستخدم تحول للمنطقة الزمنية.
- المبلغ ككائن يحوي `amount`, `currency`, `precision`، ولا يستخدم float غير موضح.

## المرفقات

- endpoints مستقلة ومحمية وتتحقق من الدور وملكية السجل.
- واجهة Odoo الحالية تقبل JPEG/PNG/WebP/HEIC/PDF بحد 15 ميجابايت للمرفق،
  وتمنع ربط مرفق تابع لفرع أو سجل آخر.
- endpoint المستقبلي يطبق allowlist والحد نفسه مبدئيًا، مع فحص اسم الملف
  والمحتوى قبل اعتماد التنفيذ.
- روابط تنزيل قصيرة العمر، ولا تكشف مسار filestore.
- مدة رابط التنزيل وآلية فحص المحتوى تعتمد قبل نشر endpoint.

## سجل التدقيق

الأحداث المهمة تسجل:

- `event_code`.
- المستخدم والشركة.
- `operation_source`: `odoo_web`, `flutter`, `api`, `import`.
- وقت UTC وUUID الكيان وبيانات مختصرة لا تحتوي أسرارًا.

أمر التركيب يضيف سجلًا زمنيًا مقروءًا للمستخدم إلى سجل التدقيق العام. حدث
تجاوز السعر يسجل UUID الخط وأكواد الخدمة والجزء والسعر القديم والجديد والعملة
والسبب. لا يعرض API المخطط `details_json` الداخلي.

سجل التدقيق غير قابل للتعديل أو الحذف من الواجهة.
في المرحلة الحالية تُفرض قيمة `odoo_web` خادميًا ويُتجاهل أي مصدر يرسله RPC.
يوجد مسار داخلي محمي برمز هوية غير قابل للتسلسل لتعيين `flutter` أو `api`
لاحقًا من controller مُراجع بعد المصادقة؛ لا تقبل القيمة من body أو من context
العميل. سجل التدقيق يأخذ مصدر العملية الحالية الموثوق، لا مصدر إنشاء السجل.

## Offline للفنيين

المخطط مزامنة محدودة فقط:

- قراءة مهام الفني المصرح بها.
- cursor مبني على `write_date` مع UUID.
- طابور محلي للنتائج يحمل Idempotency-Key.
- حل التعارض خادمي، ولا يخزن التطبيق كامل بيانات العملاء.

لا توجد مزامنة منفذة في هذه المرحلة.

## الاختبارات المطلوبة

- OpenAPI validation وcontract tests لكل endpoint.
- integration tests للصلاحيات وتعدد الشركات.
- حالات token منتهي، شركة غير مسموحة وrecord rule.
- idempotency وإعادة المحاولة والتعارض.
- رفع ملفات مخالفة والحجم الزائد.
- عدم تسريب stack trace.
- توافق مراحل UX والأدوار بين Odoo وFlutter.

## مخاطر وقرارات حالية

- المصادقة لم تعتمد بعد؛ لذلك لم ننشر controllers.
- UUID أضيف للكيانات الأساسية من الآن لتجنب ترحيل تعاقدي لاحق.
- الحقول على نماذج Odoo الأساسية تحمل بادئة `wof_` لتجنب التصادم مع موديولات
  أخرى (`res.company`, `res.users`, `res.partner`, `product.product`)، بينما
  يعرض عقد API الاسم الموحد `public_uuid`.
- سجل التدقيق موجود كأساس؛ سياسة الاحتفاظ والأرشفة تحتاج اعتمادًا قبل الإنتاج.
- `write_date` مناسب كبداية للمزامنة، لكن cursor النهائي سيعتمد بعد قياس حجم البيانات.
- موافقة العميل في MVP هي Boolean مع مرجع اختياري وليست OTP أو توقيعًا رقميًا.
- المواد داخل أمر التركيب سجل استخدام فقط؛ لا توجد حركة `stock.move` حتى مرحلة
  تكامل المخزون.
- روابط أمر البيع والفاتورة والضمان قراءة فقط في هذه المرحلة، ولا يدعي النظام
  إنشاءها أو ترحيلها.
